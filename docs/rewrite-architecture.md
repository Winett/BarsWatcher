# BarsWatcher (rewrite) — целевая архитектура (предложение)

Черновик архитектуры на основе `rewrite-vision.md`. Спорные места помечены
«(обсуждаемо)».

---

## 1. Топология: модульный монолит, два процесса

Полноценные микросервисы (отдельные репозитории/деплои/контракты между
сервисами) для этого проекта избыточны: это стоимость согласования и
эксплуатации без выигрыша на текущем масштабе. Но разделять **«обработку
Telegram»** и **«воркер опросов»** действительно правильно: тяжёлые и
медленные запросы к БАРС/ОСЭП не должны задерживать ответы боту, и наоборот.

Предложение: **одна кодовая база, два entrypoint-процесса** (docker-compose:
`bot`, `worker`, `postgres`, `redis`):

```
                 ┌──────────────┐   Redis-очередь    ┌──────────────┐
 Telegram ⇄      │    bot       │ ⇄  событий          │   worker     │  ⇄ БАРС
                 │ aiogram: UI, │   (arq / Redis)   │ планировщик, │  ⇄ ОСЭП
                 │ FSM, команды │                     │ опросы, diff │
                 └──────┬───────┘                     └──────┬───────┘
                        │            PostgreSQL               │
                        └─────────────────────────────────────┘
```

- **bot** — единственный владелец Telegram-стороны: хендлеры, FSM (ввод
  кредов/кода 2FA), клавиатуры, живые панели; публикует команды в очередь
  («проверить сейчас», «включить отслеживание»); потребляет доменные события
  (`marks.changed`, `mail.received`, `service.status_changed`, ...) и
  отправляет сообщения. Один владелец доставки в Telegram = проще лимиты и
  порядок сообщений.
  **Решение: bot — единая точка входа в Telegram и ровно один экземпляр.**
- **worker** — единственный, кто ходит в БАРС/ОСЭП: планировщик (тик →
  «пора проверить»), обработчики проверок (fetch → diff → публикация
  событий), мониторинг доступности, напоминания. Публикует доменные события
  в очередь.

Оба процесса — один и тот же код (`src/`), различаются только композиционным
корнем: какие обработчики зарегистрированы.

Вариант «worker шлёт в Telegram напрямую» отклонён: в Telegram пишет только
bot.

### Очередь событий — arq (решение)

Транспорт — **arq** (async-задачи поверх Redis): async-native (укладывается в
aiogram + async SQLAlchemy), Redis уже есть в зависимостях, из коробки
повторы с backoff, таймауты задач, cron-подобное расписание, переживание
рестартов. Событие = задача `dispatch(event)` с типизированным payload; над
arq — тонкая абстракция `events/` (publish + реестр обработчиков), чтобы код
не зависел от транспорта.

Почему не голые Redis Streams: пришлось бы самим писать consumer groups,
ретраи (XCLAIM) и DLQ — на этом масштабе выигрыша это не даёт. Если позже
понадобится настоящий broadcast-fan-out или replay, меняем реализацию
`events/bus.py` на Streams, не трогая обработчики.

1. **Очередь/события** — arq на Redis: события переживают рестарт процессов,
   доставка at-least-once, повторы с backoff встроены.
2. **Кэш снимков для diff** — как сейчас, с автоматическим TTL.

События сериализуются в JSON с обязательными `event_id`, `type`, `occurred_at`,
`payload`; обработчики идемпотентны (дедупликация по `event_id`).

## 2. Структура кода

```
src/
  core/               config, logging, security (шифрование), DI-контейнер
  events/
    contracts.py      типизированные события (dataclass/pydantic)
    bus.py            публикация/подписка поверх Redis Streams
  db/
    models/           user, bars, osep, config, monitoring
    repositories/     + uow
  integrations/
    bars/             auth (2FA), api-клиент, парсинг оценок
    osep/             OWA-клиент (Exchange service.svc, не imap/pop),
                      перечень папок, conversation'ы, вложения
  services/           доменная логика: diff оценок, роли, напоминания,
                      статистика, доступность
  workers/
    scheduler.py      единственное место с таймерами
    handlers/         обработчики событий (check_marks, check_mail,
                      availability, reminders)
  transport/
    telegram/         хендлеры, клавиатуры, states, middlewares
```

Принцип: **обработчик — это зарегистрированная функция на событие**. Новая
фича = новые события + новые обработчики; существующие потоки не трогаем.

## 3. Каталог событий

| Событие | Источник | Кто обрабатывает | Результат |
|---|---|---|---|
| `poll.due {user, service}` | планировщик | worker: check_marks / check_mail | доменные события ниже |
| `check.requested {user, service}` | bot (кнопка «проверить сейчас») | worker: тот же обработчик, что и для poll.due | idem |
| `marks.changed {user, diff}` | check_marks | bot: notify_marks | сообщение «оценка изменилась» |
| `mail.received {user, folder, mail}` | check_mail | bot: notify_mail | письмо + вложения; большая вставка → пометка |
| `service.status_changed {service, up, since}` | availability | monitoring (запись в журнал) + bot (уведомление админу, если включено) | |
| `auth.2fa_required {user, service}` | check_marks / auth | bot: спросить код 2FA | FSM-состояние |
| `auth.2fa_code_resent {user, service}` | bot (кнопка «Отправить код снова») | worker: повторная отправка кода | сообщение «код отправлен повторно» |
| `auth.failed {user, service, reason}` | auth | bot: уведомить пользователя | статус INVALID_CREDS |
| `reminder.due {user}` | планировщик | bot: notify_reminder | напоминание о парах (v2) |

Тот же паттерн «событие → обработчик → новые события» для ОСЭП и БАРС
симметричен, как и просил.

## 4. Схема БД (PostgreSQL)

```
users                     id, telegram_id (unique), username, is_active,
                          is_blocked, created_at
admins                    user_id → users

bars_credentials          user_id (unique), login, password (EncryptedString)
bars_profile              user_id (unique), fio, group,
                          is_journal_responsible (ответственный за журнал)
bars_state                user_id (unique), status (WatchStates), cookies,
                          next_check, last_check_at, last_success_at,
                          last_error_message, last_error_datetime
bars_settings             user_id (unique), tracking_enabled, show_marks,
                          reminders_enabled, reminder_time, reminder_weekdays

osep_credentials          user_id (unique), login, password (EncryptedString)
osep_state                user_id (unique), status, next_check,
                          last_check_at, last_error_*
osep_settings             user_id (unique), tracking_enabled, blacklist

global_settings           poll_interval, error_timeout, ... (одна строка)
user_overrides            user_id (unique), только переопределяемые поля
                          (NULL = взять глобальное)

service_status_log        service, started_at, ended_at, is_up
                          (журнал доступности: интервалы up/down)
```

**Слияние настроек — по-полевое:** `effective[field] = personal[field] ?? global[field]`.
Пример: глобально `poll_interval=60s`, `error_timeout=300s`; персонально
указан только `error_timeout=600s` → итог `poll_interval=60s`,
`error_timeout=600s`. (Имена полей условные.)

**Определение ответственного за журнал:** при подключении и периодически при
получении профиля — запрос своей группы в БАРС → сравнение логина со списком
ответственных → сохранить `is_journal_responsible`. Точная роль (староста /
зам) не различается — это осознанное упрощение.

## 5. Ключевые потоки (последовательности)

### 5.1 Подключение БАРС (с 2FA)

```
/start → [БАРС] → панель (Включено/Выключено) → [Включить] → «Попытка авторизоваться»
  ├─ креды есть → auth attempt
  └─ кредов нет → FSM ввода логина/пароля → save (encrypted) → auth attempt
       auth ok → сохранить куки, status=ACTIVE, запросить профиль/группу
                 → определить is_journal_responsible → авто-включение
                   отслеживания и уведомлений → панель «Включено»
                   («Время последнего запроса: НЕТ»)
       auth 2FA → событие auth.2fa_required → бот: «Введите код 2FA, он
                  отправлен вам на ...» + [Отмена]; ожидание ввода с таймаутом
                  (по истечении — отмена)
                  ├─ код верен → auth attempt #2 → см. «auth ok»
                  └─ код неверен → «Код введён неверно» + [Отправить код
                     снова] (auth.2fa_code_resent, сообщение «...отправлен
                     повторно») / [Повторить ввод] (сообщение «Введите код
                     2FA») → обе ветки в ожидание ввода
       auth fail → событие auth.failed → «Неверный логин или пароль» (alert)
                   → status=INVALID_CREDS
  сервис недоступен → «Включить» заблокировано (проверка доступности при
                      каждом подключении)
```

### 5.2 Опрос оценок (worker)

```
планировщик: tick → для user с tracking_enabled и next_check <= now
  → publish poll.due(user, bars)
check_marks:
  → доступность сервиса? нет → circuit open, publish service.status_changed
  → fetch оценок → diff со снимком в Redis (TTL)
  → изменились → publish marks.changed(user, diff)
  → обновить снимок, next_check, last_check_at
notify_marks (bot): «Оценка по X: 4 → 5»
```

### 5.3 Опрос ОСЭП (worker)

```
poll.due(user, osep) → OWA API: счётчики папок → сравнить со снимком
  (total_count по каждой папке; служебные папки игнорируются:
   Отправленные, Удалённые, Черновики, Нежелательная почта, Исходящие,
   Журнал, Задачи, Заметки, GAL Contacts, Recipient Cache, ...)
  → счётчик вырос → дозабрать новые conversation'ы этой папки
  → publish mail.received(user, folder, mail) на каждое
notify_mail (bot): текст письма + вложения;
  вложение > лимита Telegram → пометка «файл слишком большой, не удалось
  отправить»
blacklist отправителей — wildcard-паттерны, как в master
```

### 5.4 Доступность сервиса

```
ошибки запросов → circuit breaker: запросы стопорятся, редкие проверки
  «на пробуждение» (backoff) → сервис поднялся → сброс
смена статуса → service.status_changed → запись в service_status_log
  + (если включено в настройках) уведомление админу:
    «БАРС недоступен с HH:MM» / «БАРС снова доступен»
```

### 5.5 Напоминания о парах (только для ответственных)

```
v1: планировщик, ежедневно в 18:00 → reminder.due(user) для
    is_journal_responsible && reminders_enabled → бот: «Напоминание:
    проставьте пары»
v2: персональный график (дни недели + время)
```

### 5.6 Полный цикл повторной проверки (от и до)

Механика «проверить, не изменилось ли» — три слоя: **планировщик** (когда
проверять), **обработчик проверки** (одна попытка), **ретраи и
отказоустойчивость** (что делать при ошибке).

**Слой 1. Планировщик** (worker, единственный таймер в системе).
- Расписание живёт в БД (`*_state.next_check`), а не в памяти — рестарт
  ничего не теряет.
- Тик каждые ~10 секунд: выбрать пользователей с включённым отслеживанием и
  `next_check <= now`, поставить каждому в очередь событие
  `poll.due(user, service)` (одна проверка = одна задача в arq).
- При постановке `next_check` сразу сдвигается на текущий интервал — упавшая
  или задублированная задача не породит очередь дублей; обработчик после
  попытки уточняет `next_check` своим значением.
- Интервал = по-полевое слияние персональных и глобальных настроек (§4).
  Семантика авто-масштабирования переносится из master (AutoScaler): ошибка →
  интервал ×1.5 (cap = max_poll_interval), успех → ×0.7, но не ниже базового.
  Текущий интервал хранится в `*_state` и переживает рестарт.

**Слой 2. Обработчик проверки** (одна попытка сверить данные).
1. **Circuit breaker**: сервис помечен «недоступен» и не пора пробуждающему
   пингу → выходим без сетевого запроса (в мёртвый сервер не стучимся).
2. **Авторизация**: жива ли сессия (куки/канарейка OWA, сессия БАРС); если
   протухла — один автоматический re-login по сохранённым кредам. Нужен 2FA →
   статус WAITING_2FA, событие `auth.2fa_required`, опросы пользователя на
   паузе до ввода кода.
3. **Fetch** — один снимок: БАРС — оценки; ОСЭП — счётчики папок (§5.3).
4. **Diff** со снимком в Redis (TTL). Изменения → `marks.changed` /
   `mail.received` (для ОСЭП при росте счётчика дозабираем сами письма).
5. **Фиксация при успехе**: обновить снимок в Redis, `last_check_at`,
   `last_success_at`, `next_check = now + текущий интервал`. Снимок
   обновляется только при успехе — повторная проверка не пришлёт дубликат
   уведомления.

**Слой 3. Ретраи и отказоустойчивость.** Ошибки делятся на классы:
- **Транзиентная** (timeout, 5xx, сеть) → быстрые повторы самой задачи в arq
  с backoff (например 3 попытки: +0с, +30с, +120с). Все упали → это «ошибка
  итерации»: `last_error_*`, интервал ×1.5 (cap max_poll_interval), следующая
  попытка — по расписанию через увеличенный интервал. Быстрые ретраи не
  копаются вечно — расписание продолжает работать.
- **Ошибка авторизации** (401, мёртвые куки) → сначала один re-login; не
  помогло → `auth.failed`, статус INVALID_CREDS, опросы стопорятся до
  действий пользователя (бот сообщает).
- **Сервис лежит** (connection refused, 5xx/503, полный timeout) → запись в
  `service_status_log` («недоступен с HH:MM»), `service.status_changed(down)`
  → уведомление админу (если включено). Дальше circuit breaker: обычные
  проверки не шлют запросы; раз в пробуждающий интервал (backoff, например
  5→10→20 мин, cap 30 мин) — один лёгкий запрос-«пробуждение». Ответил →
  `service.status_changed(up)`, сброс интервалов к базовому, проверки
  возобновляются.

**Идемпотентность и дубли.** У каждого события есть `event_id`, обработчики
дедуплицируют. Уведомления привязаны к diff'у снимка, а не к факту проверки:
повторная или задублированная задача не создаёт повторных сообщений.

**Мини-таймлайн.**
- 12:00:00 тик → `poll.due(user7, bars)` → успех, изменений нет →
  `next_check` 12:03:00.
- 12:03:00 → оценка изменилась → `marks.changed` → bot: «Математика: 4 → 5».
- 12:06:00 → timeout → 3 быстрых ретрая в arq → мимо → интервал ×1.5
  (3 → 4.5 мин) → `next_check` ≈ 12:10:30.
- 12:10:30 → connection refused → circuit open: «БАРС недоступен с 12:11»
  админу, пробуждающий пинг через 5 мин; 12:16 пинг ОК → «БАРС снова
  доступен», интервал сброшен к базовому.

## 6. Статистика (только админ)

Отдельные таблицы не нужны — SQL по `users`/`*_credentials`:

- всего пользователей: `count(users)`;
- подключено (к чему-то): есть креды БАРС или ОСЭП;
- используют БАРС / используют ОСЭП: по `*_credentials` (+ флаг
  tracking_enabled, если нужна строгость);
- новые за сегодня / текущую неделю / прошлую неделю / месяц: по
  `users.created_at` (границы недели — по понедельникам, уточнить).

Выдача: админ-меню в боте (`/admin` → «Статистика»), сообщение с цифрами.

## 7. Дорожная карта

1. **Каркас:** config, logging, security, модели + миграции (user/bars/osep/
   config/monitoring), repositories + UoW, event bus на Redis Streams,
   запускаемые `bot` и `worker`, `/start` с приветствием и меню.
2. **БАРС:** интеграция авторизации (с 2FA), профиль + определение
   ответственного, опрос оценок + diff + уведомления, панель состояния,
   настройки отслеживания.
3. **ОСЭП:** интеграция (все папки), пересылка писем с вложениями (+ пометка
   о больших файлах), настройки (blacklist).
4. **Доступность:** circuit breaker + журнал up/down + уведомления админу с
   настройкой вкл/выкл.
5. **Напоминания о парах v1:** ежедневно в 18:00 для ответственных с
   переключателем.
6. **Статистика для админа.**
7. **v2-хвост:** гибкий график напоминаний, персональные настройки опроса
   (по-полевое слияние с глобальными) — если не вошли в этап 2/3.
8. **Миграция данных с master** (в самом конце): перенос пользователей и
   кредов из старой таблицы `users` в новые таблицы (пароли — через
   шифрование).

Этапы 2 и 3 независимы — можно делать параллельно или менять порядок.
