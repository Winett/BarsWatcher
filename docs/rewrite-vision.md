# BarsWatcher (rewrite) — видение проекта (согласованная версия)

Документ фиксирует цель переписывания и поведение будущего бота.
Рабочая ветка — `rewrite`; продакшен-ветка в репозитории — `master`.
Раздел 7 содержит решения по всем открытым вопросам (ответы пользователя).

---

## 1. Зачем переписывание (4 цели)

1. **Расширяемость.** Архитектура должна позволять добавлять новые фичи простым
   добавлением модуля/обработчика, а не вмешательством в существующие потоки.
2. **Событийная модель вместо вечных циклов.** Сегодня на каждого пользователя
   крутится `while True` внутри живого объекта вотчера, а всё состояние держится
   в Runtime (память процесса). Хочется: появляется событие → его обрабатывает
   зарегистрированный обработчик → обработчик может породить следующие события.
   Состояние — в БД/кэше, события — не в ОЗУ процесса (очередь, см. §7.4).
3. **Реорганизация БД.** Сейчас одна таблица `users` — «всё в куче». Нужно
   разделить на самостоятельные контексты (ядро/пользователь, БАРС, ОСЭП,
   мониторинг, статистика). Плюс хранить признак «ответственный за журнал»
   (староста/зам) — основа фичи напоминаний о проставлении пар.
4. **Статистика.** Только для админа(-ов): см. §6.

---

## 2. Что есть в коде (коротко)

**master (продакшен):** aiogram-бот (`handlers/`, `keyboards/`, `states/`,
`middlewares/`) + подсистема `watchers/`: `BaseWatcher` с бесконечным циклом
`run()` на каждый аккаунт, `WatcherManager` держит живые инстансы, Redis-кэш
снимков для diff (с TTL), `AutoScaler` для разгона интервала при ошибках,
`connection_monitor` для доступности сервера, синглтон `EventService`
(in-process pub/sub). БД: одна «широкая» таблица `users` +
`global_config`/`user_config`.

**rewrite (начат):** скелет `src/` — `core` (config, logger, security с
Fernet-шифрованием), `db/models` уже разнесены по контекстам (`user.py`,
`bars.py`, `osep.py`, enums, EncryptedString), `repositories` с UoW.

## 3. Пользовательские сценарии

### 3.1 Вход и `/start`

`/start` → **приветственное сообщение**: «Добро пожаловать в бот по
отслеживанию БАРС и ОСЭП. Выберите, что хотели бы начать отслеживать» +
кнопки направлений:

- **БАРС**
- **ОСЭП**

Язык интерфейса — русский.

### 3.2 БАРС

Панель БАРС (живое сообщение) в двух состояниях, кнопки: **Включить /
Отключить**, **(Изменить/Добавить) данные для входа**, **Настройки**,
**Обновить**, **Назад**.

- **Выключено:** «Отслеживание БАРС: Выключено / Состояние БАРС: работает /
  не работает / Логин: текущий или Нет / Если БАРС не работает, временно не
  получится подключить эту функцию».
- **Включено:** «Отслеживание БАРС: Включено / Состояние БАРС: работает /
  не работает / Время последнего запроса / Логин: текущий».

Подключение (кнопка «Включить» → «Попытка авторизоваться»), три исхода:

1. **Успех** → «все системы включаются»: отслеживание и уведомления
   включаются автоматически, исходное сообщение меняется на панель
   «Включено» («Время последнего запроса: НЕТ») → «Уведомления о БАРС
   включены». Сессия/куки сохраняются, дальше система работает от имени
   пользователя.
2. **Требуется 2FA** → «Введите код 2FA, он отправлен вам на ...» + кнопка
   **Отмена**; ожидание ввода ограничено по времени (по таймауту ввод
   отменяется). Дальше:
   - код верен → «Уведомления о БАРС включены»;
   - код неверен → «Код введён неверно» + кнопки **Отправить код снова**
     (сообщение меняется на «Введите код 2FA, он был отправлен вам
     повторно») и **Повторить ввод** (сообщение меняется на «Введите код
     2FA»); обе ветки возвращаются в ожидание ввода.
3. **Провал** → «Неверный логин или пароль» (как alert).

Если данных для входа нет — сначала FSM ввода логина/пароля (кнопка
«(Изменить/Добавить) данные для входа»), затем попытка авторизации.

Дальше по сценарию:

4. Система периодически опрашивает БАРС, сверяет оценки (и пропуски) со
   снимком; **если изменились — уведомляет пользователя** (предмет,
   старая → новая оценка).
5. **Ответственный за журнал (староста/зам).** Определить точную роль
   (староста или зам) нельзя, поэтому делаем проще: запрашиваем у БАРС данные
   своей группы и сравниваем логин пользователя со списком ответственных за
   журнал. Совпало → пользователь «ответственный». Такому пользователю в
   настройках появляется опция **«напоминать о проставлении пар»**.
6. **Доступность:** при каждом подключении проверять, доступен ли сервис.
   Если сервис недоступен — подключить отслеживание временно нельзя.

**Настройки для БАРС:**

- Уведомления об оценке — с возможностью **скрывать оценку** (само значение
  в уведомлении не показывать);
- Уведомления о пропусках;
- Уведомления о проставлении пар — только для ответственных за журнал.

### 3.3 ОСЭП

Подключение — **через OWA API** (Microsoft OWA, `service.svc` на
mail.mpei.ru), **не IMAP/POP**: свой api-клиент, как в master
(`watchers/api/osep_api.py`, `watchers/auth/osep_auth.py`).

Задача предельно узкая:

- **Только новые письма** — сразу переслать пользователю в Telegram.
- **Вложения** отправлять тоже. Если файл слишком большой для Telegram —
  отправить пометку, что файл слишком большой и его не удалось выслать.
- Проверять **все содержательные папки**; служебные и исходящие **не
  обрабатывать**: Отправленные, Удалённые, Черновики, Нежелательная почта,
  Исходящие, Журнал, Задачи, Заметки, GAL Contacts, Recipient Cache и т.п.
  (игнор-лист как в master, `osep_watcher.py`).
- Ничего другого от ОСЭП не требуется.

Панель ОСЭП — зеркало панели БАРС (Включить/Отключить, данные для входа,
Настройки, Обновить, Назад); при включении — «Попытка авторизоваться» с
исходами успех / «Неверный логин или пароль» (2FA у ОСЭП нет). Настройка —
**чёрный список** отправителей, от которых не присылать письма.

### 3.4 Напоминания о проставлении пар (фича, подлежащая проработке)

- **v1 (стационарно):** раз в день в фиксированное время — 18:00.
- **v2 (гибкий график):** пользователь сам выбирает дни и время напоминаний,
  чтобы каждому было комфортно.
- Логика «забыли/не забыли» — отдельная проработка позже.

### 3.5 Панели и кнопки (общее)

Все панели — **живые сообщения** (редактируются при изменении состояния):

- **Обновить** — освежает данные самого сообщения (состояние, время
  последнего запроса); это **не** «проверить прямо сейчас».
- **Назад** — возврат в приветствие `/start`.
- **Включить/Отключить** — включение отслеживания (через авторизацию) и
  выключение.
- **(Изменить/Добавить) данные для входа** — FSM ввода логина/пароля.
- **Настройки** — экран настроек сервиса (см. §3.2, §3.3).

### 3.6 Дополнительные команды

- `/services` — доступность обоих сервисов:
  «БАРС: Доступен / Не доступен (с 18:39 21.09.2026)»,
  «ОСЭП: Доступен / Не доступен (с 17:34 21.09.2026)», кнопка «Обновить».
- `/statistic` (только админ) — статистика из §6, кнопка «Обновить».

## 4. Общие инфраструктурные требования

1. **Не стучаться в мёртвый сервис.** Если БАРС/ОСЭП лежит — вотчеры не
   отправляют запросы впустую (backoff / circuit breaker; в проде уже есть
   зачатки: `connection_monitor`, `AutoScaler`).
2. **Журнал доступности.** Фиксировать, когда сервис был доступен, когда и как
   долго недоступен (лог + БД для статистики/истории).
3. **Уведомления о доступности — отдельная функция.** Сервис упал →
   «БАРС недоступен с HH:MM», поднялся → «БАРС снова доступен». Пока шлём
   **только админу**, при этом есть **настройка включения/выключения** этой
   функции.
4. **Событийная модель.** Механика:
   - планировщик (единственное место с таймером) роняет событие
     «для пользователя X пора проверить сервис»;
   - обработчик проверки идёт в сервис, сверяет со снимком; при изменениях
     роняет другое событие («изменились оценки» / «новое письмо»);
   - обработчик уведомления ловит эти события и отправляет сообщение
     пользователю (+ вложения для ОСЭП);
   - события доступности сервиса (`up`/`down`) обрабатываются так же:
     запись в журнал + уведомление админу.

## 5. База данных

Контексты (в rewrite уже начато):

- **user** — профиль Telegram-пользователя, админ-права;
- **bars** — креды (шифрованные), профиль (ФИО, группа,
  **признак «ответственный за журнал»**), состояние вотчера (статус, куки,
  интервал, следующая проверка, последние ошибки), настройки (отслеживание,
  показывать оценки, напоминания);
- **osep** — креды (шифрованные), состояние, настройки (чёрный список
  отправителей);
- **мониторинг** — журнал доступности сервисов (интервалы up/down);
- **конфигурация** — глобальные настройки + персональные переопределения
  (см. §7.7);
- **статистика** — на первом этапе отдельных таблиц не требует (считается
  запросами по существующим данным).

Ограничение: **1 аккаунт на 1 сервис на пользователя** (unique по
пользователю в каждой таблице кредов).

Снимки данных для diff (оценки, письма) — Redis с автоматическим TTL,
как сейчас (§7.5).

## 6. Статистика

Для обычных пользователей статистики **не делаем**.

Для админа:

- сколько людей всего в боте;
- из них сколько подключено;
- сколько используют БАРС / сколько используют ОСЭП;
- сколько новых людей: за сегодня, за текущую неделю, за прошлую неделю,
  за месяц.

## 7. Решения по открытым вопросам

1. **Роль старосты/зама.** Точно определить нельзя → сравниваем логин
   пользователя с ответственными за журнал в его группе (запрос своей группы
   в БАРС). Совпало = «ответственный».
2. **Расписание напоминаний.** v1 — стационарно ежедневно в 18:00; затем v2 —
   гибкий график вплоть до «в какой день в какое время».
3. **Статистика.** Пользователям — не делаем. Админу — метрики из §6.
4. **События и процессы.** События не хранятся в ОЗУ процесса — используем
   Redis-очередь (или аналог). Архитектура обсуждается отдельно: не полные
   микросервисы, а разделение на «обработка Telegram» и «воркер опросов» —
   см. `rewrite-architecture.md`.
5. **Снимки для diff.** Redis с автоматическим TTL — как сейчас, вариант
   признан хорошим.
6. **Большие вложения ОСЭП.** Если файл не удалось отправить (слишком
   большой) — присылаем пометку об этом.
7. **Настройки опроса.** Общий + персональный уровни, слияние **по-полевое**:
   персональное значение поля переопределяет глобальное, не указанное поле
   берётся из глобального. Пример (имена переменных условные): глобально
   `poll_interval=60s`, `error_timeout=300s`; персонально указан только
   `error_timeout=600s` → итог: `poll_interval=60s`, `error_timeout=600s`.
8. **Аккаунты.** Один аккаунт на один сервис на пользователя.
9. **Уведомления о доступности сервиса.** Пока только админу + настройка
   вкл/выкл этой функции.
10. **Язык.** Только русский.
