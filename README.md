# BarsWatcher

Telegram-бот для отслеживания оценок в БАРС и писем в ОСЭП (mail.mpei.ru, OWA).

Ветка `rewrite` — переписывание ядра: событийная модель (очереди вместо
вечных циклов), разделённые контексты БД, воркер опросов отдельно от Telegram.

Документы проекта:

- `docs/rewrite-vision.md` — видение и пользовательские сценарии;
- `docs/rewrite-architecture.md` — целевая архитектура, события, схема БД;
- `docs/bars-api.md` — фактический web-API БАРС (вход/2FA/оценки/пары).

## Статус

Реализовано **ядро** (этап 1 без Telegram-слоя):

- конфиг/логирование/шифрование секретов;
- модели БД: `users`, `bars_*`, `osep_*`, `global_settings`/`user_overrides`,
  `service_status_logs` + миграции `0001`–`0002`;
- репозитории + UnitOfWork;
- шина событий на arq (Redis): `publish`/`subscribe`/`dispatch_event`,
  очереди `worker` (проверки) и `bot` (уведомления, потребитель — следующий
  этап);
- планировщик (тик → событие `poll.due`) и обработчики проверок:
  circuit breaker, авторизация (с точкой расширения под 2FA), diff со снимком
  в Redis (TTL), авто-масштабирование интервала (ошибка ×1.5 / успех ×0.7),
  журнал доступности + события `service.status_changed`;
- интеграции: порты `BarsClient`/`OsepClient`, **реальные клиенты**: БАРС
  (`src/integrations/bars/`: вход + 2FA с восстановлением сессии,
  оценки/пропуски, ответственные за журнал, расписание) и ОСЭП/OWA
  (`src/integrations/osep/`: `service.svc`, папки/письма/вложения,
  авто-relogin); `INTEGRATION_MODE=real`. Тестовые режимы:
  `INTEGRATION_MODE=sim` — «настоящие» запросы по сохранённым ответам:
  каждый fetch читает HTML-ответы из `simdata/bars/*.html` и прогоняется
  через реальные парсеры (ОСЭП в sim — случайная симуляция почты);
  `INTEGRATION_MODE=file` — ответы берутся из `simdata/*.json`,
  которые можно править руками и смотреть, как срабатывают события.
- **тестирование оповещений**: правьте файлы ответов (`simdata/bars/*.html` —
  оценки/пропуски/профиль; `simdata/*.json` в file-режиме) — в тестовых
  режимах проверка идёт каждые `SIM_POLL_INTERVAL_SECONDS` (по умолчанию 10),
  изменения превращаются в события и приходят уведомлениями; кнопка
  «Обновить» в панели запускает проверку немедленно. Правила границ семестра:
  новые дисциплины игнорируются (в начале семестра список дополняется);
  смена семестра не даёт уведомлений (совпадающие дисциплины не шлют «5 → .»)
  — сменившийся семестр становится новой базой. Проверить смену семестра в
  тестовом режиме можно переменной `SIM_SEMESTER=<метка>`: смените её значение
  и дождитесь проверки — уведомлений не будет, следующие изменения в том же
  семестре уведомляются как обычно.
- **время везде GMT+3** (панели, уведомления); **напоминания о проставлении
  пар** — раз в день в 18:00 GMT+3 ответственным за журнал с включённой
  настройкой «Пары»; в тестах проверить можно `SIM_REMINDER_INTERVAL=60`
  (напоминание придёт в течение минуты);
- **`/suggestion` и `/report`** — идеи и жалобы: сообщение копируется и
  направляется администраторам;
- **проверка проставления пар** (для ответственного за журнал): сверка
  занятий журнала с расписанием — пара есть в расписании, а в журнале нет;
  статус «требуется корректировка»; «на рассмотрении» без отметок студентов.
  «Согласовано» или «на рассмотрении» с отметками — всё ок, не напоминаем;
- **напоминания с деталями**: в напоминании перечисляется, что именно не так
  («25.09.26 Механическая физика 1 пара (9:20-10:55), лабораторная работа
  (Преподаватель) стоит статус «требуется корректировка», студенты не
  отмечены»); если все пары в порядке — напоминание не отправляется;
- **«🔍 Сверка пар с расписанием»** (в настройках БАРС, ответственным):
  сверка с начала семестра по текущую дату — выводятся только пары, которых
  нет в журнале («За 20.09.26 пропущена пара 2 по Дифференциальные уравнения
  (Преподаватель)»). Пары разных групп/подгрупп в одно время одной парой
  считаются одной — ложных «непроставленных» не будет;
- **включение ОСЭП не шлёт «старые» письма**: при первом запуске (или после
  включения) счётчики папок просто запоминаются — уведомления идут только о
  письмах, пришедших после; если в письме есть вложения — в конце уведомления
  добавляется строка «Есть вложения!», сами файлы скачивает worker в общий
  кэш и бот отправляет их следом;
- **`/clearqueue`** (админ) — вычистить ожидающие в Redis события (очереди
  bot и worker): бот перестаёт доставлять накопленные тестовые уведомления;
- **скорость отправки**: не более 20 сообщений в секунду (лимитер + повтор
  при 429 TelegramRetryAfter).

## Запуск

```bash
uv sync
cp .env.example .env      # заполнить: SECRET_KEY, токен, БД, Redis
docker compose up -d      # postgres + redis

uv run alembic upgrade head        # схема БД
uv run python scripts/seed_demo.py # демо-пользователь с включённым отслеживанием
uv run python bot.py               # Telegram-бот (long polling)
uv run python worker.py            # воркер: планировщик + очередь проверок
```

Логи (`logs/`) покажут цикл: тик планировщика → `poll.due` → проверка →
diff → события `marks.changed`/`mail.received` (уходят в очередь `bot`,
её обрабатывает сам бот → уведомления в Telegram). В логах также видно:
весь пользовательский ввод (`ввод | Message` / `ввод | CallbackQuery`,
пароль пишется как «<пароль, скрыт>»), отправленные уведомления (БАРС —
текст целиком; письмо — тема, от кого и сколько вложений), скачивание и
удаление файлов вложений (`вложение скачано` / `вложение удалено`).

### Тестовый стенд в Docker

Один образ — два процесса (`bot.py`, `worker.py`), плюс postgres и redis.
`.env` обязателен; `DB_HOST`/`REDIS_URL` в контейнерах переопределяются
автоматически (compose подставляет имена сервисов).

```bash
cp .env.example .env      # заполнить: SECRET_KEY, токен, креды БД
docker compose up -d --build

docker compose logs -f bot worker   # логи
docker compose run --rm bot python scripts/seed_demo.py  # демо-пользователь
docker compose down                 # остановить (данные в томе pgdata)
```

Миграции (`alembic upgrade head`) выполняются одноразовым сервисом `migrate`
перед стартом `bot`/`worker`.

Полезное:

```bash
uv run python scripts/smoke_core.py        # smoke ядра без БД/Redis
uv run python scripts/smoke_bars_parser.py # парсеры БАРС на HTML-шаблонах
uv run python scripts/test_bars_fixtures.py # парсеры на реальных *.html из simdata/bars
uv run python scripts/test_bars_client.py  # живой тест клиента БАРС (вход, 2FA, данные)
uv run python scripts/smoke_osep_parser.py # ОСЭП: разбор JSON OWA + кэш вложений
SIM_DOWN=1 uv run python worker.py         # сервис «недоступен» — circuit breaker
```

Sim-договорённости для ручных тестов: пароль `wrong` — неверные креды;
логин с префиксом `2fa` — запрос 2FA (код `0000` — неверный, другой — верный);
сервис «лежит» — `simdata/service.json` (`{"is_up": false}` или `{"bars_up": false}`)
либо `SIM_DOWN=1`.

## Админка

`/admin` в боте — только для администраторов (обычным пользователям команда
не отвечает вообще). Админы и начальные глобальные настройки при **первом**
запуске импортируются из `.env` (`ADMINS` — список **telegram_id**,
`POLL_INTERVAL_SECONDS` и соседние — настройки); дальше всё изменяется из
админки и живёт в БД (удалённый через админку админ не вернётся после
перезапуска). Администраторы из `ADMINS` помечены 🔒 и не удаляются.

- ⚙️ **Глобальные настройки**: интервалы опроса, таймауты, авто-масштаб;
- 👤 **Пользователи**: поиск по telegram_id/@username — статусы БАРС/ОСЭП,
  профиль, индивидуальные настройки (кастомное перекрывает глобальное
  по-полево, в карточке видно источник значения); в карточке —
  **заблокировать/разблокировать**, **снять/вернуть активность** (у
  заблокированных и неактивных вотчеры выключаются, рассылка им не
  отправляется) и кнопка **«🔄 Обновить»**; если пользователь сам заблокировал
  бота — при попытке отправки он автоматически помечается неактивным и
  вотчеры выключаются; заблокированные админом полностью игнорируются ботом;
- 📣 **Рассылка**: сообщение всем активным — с предпросмотром «как увидят
  пользователи» и подтверждением отправки;
- 🛡 **Администраторы**: добавление/удаление;
- 📜 **Логи**: inline-кнопки по датам (только за те даты, где логи ещё есть;
  нет лога — бот скажет об этом); плюс автоотправка вчерашнего лога админам
  каждый день в 00:00 МСК;
- 🔔 **Уведомления админам**: о новых пользователях и о том, что сервис
  поднялся/упал (тогглы).
